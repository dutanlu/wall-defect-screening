## 一、为什么不能做「演化预测」（一句话）

**数据里根本没有时间维度。** 不是技术不够，是**没有可配对的纵向观测**。

| 检查项 | 实测结果 |
|---|---|
| 标注 txt 时间戳字段 | 无（只有 5 列 `cls cx cy w h`） |
| 图片 EXIF 拍摄时间 | 抽样 400/11404 张，命中 **0** |
| 文件名日期/批次/楼号 | 无 |
| 同一栋楼多次巡检 | 无（同源多图皆为**同一次**拍摄） |
| 同一次拍摄的纵向痕迹 | **被主动去重清掉**（L1 MD5 + L2 dHash≤3） |
| 收集站 `created_at` | 字段在，但投稿 **0 条** |
| BFDD 无人机时间戳 | 有（4 个航测日），但跨天 dHash 实测 ⇒ **4 面不同的墙** |

**BFDD 跨天配对实测（§9.4.1）**：跨天最小汉明距离 11~13，同天 8~14
⇒ 同量级 ⇒ 跨天**不存在**「同一立面重拍」应有的近重复信号
⇒ 不是「没找到时间数据」，而是「**时间数据里本来就没有纵向维度**」（更强的结论）。

## 二、能做的那部分：**变化检测**（不是预测）

在拿到「同一对象 ≥2 次拍摄」之前，唯一站得住的落地物是
**配对 + 变化度量**，且必须**与弃权机制同构**：配不上就不给结论。

### 2.1 交付物

| 文件 | 作用 |
|---|---|
| `02_code/change_detect.py` | 配对判据 + 变化度量 + 反预测护栏 |
| `logs/_verify_change_detect.py` | 四情形可证伪验证（正例×2 / 反例×2） |
| `04_results/eval/change_detect_verify.json` | 验证证据（含阈值与逐例原始数值） |

### 2.2 判据（全部集中、全部注明来源）

| 参数 | 值 | 来源 |
|---|---|---|
| `max_dhash_hamming` | **10** | §9.4.1 实测：近重复 ≤6、不同立面 11~13 ⇒ 取 10 容许光照差异、仍低于不同立面 |
| `min_inlier_ratio` | 0.30 | 单应配准（可选路径）内点率下限 |
| `min_iou_match` | 0.30 | 缺陷实例配对的 IoU 下限 |
| `min_rel_width_change` | 0.20 | 相对可辨幅度（20%），低于此只报「无明显变化」 |
| `gsd_measurable_max` | 0.10 | 判读 0.3mm 裂缝的 GSD 门槛（与主线一致） |

### 2.3 验证结果（可证伪，非「永远同一答案」）

| 情形 | 期望 | 实测 | 判定 |
|---|---|---|---|
| **A** 同一面墙 + 裂缝 4px→10px | 配对成功 + 检出增宽 | `pair_ok=True`，hamming=2，Δ=**+0.250mm** | ✅ |
| **B** 同一面墙 + 亮度 +25 | 配对成功（光照≠换墙） | `pair_ok=True`，hamming=**0** | ✅ |
| **C** 两面不同的墙 | 拒配 + **不给变化量** | `pair_ok=False`，hamming=16，`changes=None` | ✅ |
| **D** 同一面墙旋转 90° | 拒配 | `pair_ok=False`，hamming=28 | ✅ |
| **E** 反预测护栏 | `is_prediction=False` | 全为 False | ✅ |

> 关键：A 与 C/D 是**互斥**结果 ⇒ 阈值既不过松（C/D 未误配）
> 也不过紧（A/B 未误拒）⇒ 判据**真的在起作用**。

## 三、反预测护栏（写死在代码里）

`change_detect.py` 的所有输出都携带：

- `is_prediction: False`（写死，不提供修改入口）
- `requires_timepoints: 3`
- `note`：本结果只描述 T1→T2 的**已发生**变化，不含速率、不含外推、不含失效时间

**为什么不给开关**：一旦给了「自动外推」的选项，下游一定有人会打开它，
然后把「变化检测」当成「演化预测」写进汇报。
护栏的意义就是**让这条误用路径在代码层面不存在**。

## 四、要让它真正「能做演化」，缺的唯一关键数据

> **同一建筑 / 同一墙面、跨不同日期、带可对齐身份键（楼号 + 位置 + 拍摄时间）的 ≥ 2 次重复拍摄。**

三个要件缺一不可：**跨日期**（非同日连拍）、**同一对象**（否则配不上）、
**可对齐身份键**（否则「同一天拍的两面墙」也会错配）。

正确顺序是**先建采集与台账机制，再谈演化预测**：

1. 收集站加字段：`building_id` / `position` / `capture_time`
   （优先读 EXIF，读不到用上传时间并**标注来源**）；
2. **去重策略分离**：训练/评估划分**继续去重**（避免泄漏），
   但**原始台账必须保留重复记录**（否则纵向数据被自己的清洗流程销毁）；
3. **最小可行验证**：同一面墙、间隔 ≥1 个月、≥2 次拍摄
   ⇒ 用 `change_detect.pair_and_diff()` 开始做**变化检测**；
4. **诚实命名**：拿到 ≥3 个时间点前，**只写「变化检测」，不写「预测」**。

## 五、对外表述（建议照抄）

> 我们**没有**做缺陷随时间的演化预测，这不是遗漏，而是数据条件的直接后果：
> 工程内不存在任何跨时间的纵向重复观测 —— 无日期字段、图片 0 EXIF、
> 同一栋楼无重复巡检、收集站投稿 0 条；唯一带时间戳的数据（BFDD）是
> 4 天的单次航测战役（且经 dHash 实测确认拍的是 4 面不同的墙）。
> 我们把这条边界写清楚，给出补足它所需的最小条件，
> 并把**在现有数据上真正能做的那部分（配对 + 变化检测）**做成了可复算的代码。
