## 二、四问的完整答法

### 问 ①　为什么选这个场景？

**一句话**：不是我们挑了一个「好做的检测任务」，而是这个场景里藏着一个
**被整个领域忽略的物理硬约束**，而我们决定正面回答它。

**三层理由**：

1. **真实刚需（实用价值）**：我国大量既有建筑进入老化期，住建部推动的「房屋体检」制度
   要求建立「一房一档」台账。但现实是三点矛盾 —— 待查存量大（仅一个地级市的既有建筑
   就达数十万栋量级）、专业鉴定力量少且单次成本高、基层巡检人员缺专业判断能力。

2. **行业真正缺的不是「更准的裂缝检测器」**，而是**能把海量日常照片快速筛一遍、
   按风险排序、告诉基层「哪几栋该优先请专业机构进场」**的工具。

3. **★ 技术上的不同寻常之处（创新性）**：调研现有外墙/混凝土缺陷检测工作
   （各类 YOLO 变体、分割网络、多任务模型），发现一个被普遍忽略的问题 ——
   **几乎所有工作都隐含假设「输入图像是合格的」**。没有人回答：
   > 「站在楼下 30 米外仰拍的一张照片，能不能用来判断这栋楼的结构安全？」

   而物理上这是硬约束：以主摄 24mm（水平 FOV≈74°）配 1200 万像素（宽 4000px）为例，
   20 米外主摄的 GSD ≈ 7.5 mm/px；而 GB 50010-2010 要求判读 0.30mm 裂缝
   需要 **GSD ≤ 0.1 mm/px**，主摄须贴近到约 **27 厘米** —— 地面拍高层根本做不到。

   **这意味着：用地面照片报「裂缝宽度 0.35mm，超限」，在物理上就是无效结论，
   无论检测模型多准。** 所以我们把任务重新定义为**筛查（screening）而非鉴定（appraisal）**。

> **配套数字（可背）**：0.3mm 裂缝要判读，需 GSD ≤ 0.1 mm/px；主摄须贴身 27cm，5x 长焦须 1.3m。

### 问 ②　数据从哪来、如何标注？

> ⚠️ 这一问是**我们此前完全没准备的**，也是本项目最需要**如实作答**的一问。

**（1）数据从哪来 —— 全部来自公开数据集，未自行拍摄**

| 来源 | 贡献类别 | 许可 |
|---|---|---|
| GreyBrick（Roboflow Universe） | 泛碱、剥落 | 公开数据集 |
| Urban（Roboflow） | 锈迹、空鼓 | 公开数据集 |
| HRCDS | **露筋** | 公开数据集 |
| `jiange1236/StructuralCrackDataset` | 裂缝（实际贡献 79 框 / 25 图） | Apache-2.0 |

汇总：经内容级去重后重建为 **2848 图 / 18262 框 / 7 类**，划分为 **1995 / 568 / 285**。

**（2）如何标注 —— 我们没有自行标注，用的是数据集自带的现成标注**

必须**主动说清楚**这一点，然后说明我们真正做的工作：

- **格式转换**：`step5_fetch_rebar.py` 把 label-studio 导出的 JSON 转成 YOLO txt 格式；
- **★ 内容级去重（我们最主要的数据工作）**：原始数据存在大量「同图不同副本」
  （目录镜像与增强变体）。我们按 **MD5 + 内容比对**做去重，实测 **2400 → 677 唯一图**；
- **★ 弃用数据集自带的划分**：这套数据自带 train/valid 划分。我们原本想直接用，
  但按 MD5 做了一次内容级核对 —— 发现 `train` 561 张唯一图、`valid` 156 张，
  其中 **40 张同时出现在两侧，占它自己验证集的 25.64%**。
  这是**数据集自带的泄漏**，我们**弃用了原划分，自己完全重划分**；
- **跨集交集自检**：重划分后 train/val/test 三集交集**全部为 0**（9 项检查全 0）；
- **类别体系对齐**：7 类缺陷类型按国标（GB 50010-2010 / JGJ 125-2016）的定义来定。

**（3）诚实边界（必须主动讲）**

- **我们没有自行标注任何一张图**，因此「标注质量」不是我们的工作量；
  我们投入的是**去重与重划分** —— 而恰恰是这一步，暴露并修掉了数据集自带的 25.64% 泄漏。
- 我们自建了一个**网友照片收集站**（`08_photo_collector`，已部署上线），
  用于未来补充真实拍摄样本；**目前投稿 0 条**，所以不影响本次任何结论。

> **如果被追问「那你凭什么说你的数据可靠」**：
> 答「不靠我标得准，靠我把不该混在一起的图分开了」——
> 并把 25.64% 泄漏 → 弃用 → 重划分 → 9 项检查全 0 这条链子讲完。

### 问 ④　预期达到什么效果、可能遇到什么困难？

> ⚠️ 这一问我们也**只准备了一半**（只有"实测效果"，没有"预期"）。
> 关键在于：**先说赛前的预期，再说实际结果，两者对照** —— 这才是评审想听的。

**（1）预期达到什么效果（赛前设定 → 实际结果）**

| 赛前预期 | 实际结果 |
|---|---|
| 输出**风险排序 + 是否需专业机构进场**，而不是法定鉴定结论 | ✅ 已实现（A/B/C/D/U 五档 + 「是否需要专业机构进场」） |
| 明确的三态输出：**可判读 / 部分可判读 / 拒绝判读** | ✅ 已实现（界面顶部状态行） |
| 去重后的独立测试集上 **mAP50 ≥ 0.65** | ✅ 实际 **0.723**（测试集 285 图 / 1646 实例） |
| 普通笔记本上 **1 秒内**出结果 | ✅ GPU 上模型推理约 9.29 ms/图，端到端几十毫秒 |

**（2）可能遇到的困难（赛前预判 → 是否真的遇到）**

| 预判的困难 | 实际情况与应对 |
|---|---|
| 公开数据集**类别不全** | ✅ 真遇到。初期只有 4 类有数据；靠补数据源（Urban / HRCDS）补齐 7 类 |
| 数据集**自带划分不可靠** | ✅ 真遇到且比预想严重 —— **25.64% 跨集泄漏**，最终弃用原划分、完全重划分 |
| **类别极不均衡**（锈迹占 69.8%） | ✅ 真遇到。如实报告，不掩饰整体 mAP 的窄区间主要由 `rust` 贡献 |
| **小样本类**导致指标不稳 | ✅ 真遇到。`spalling` 仅 30 实例 ⇒ AP 的 95% CI 半宽约 ±0.16，因此**不跨模型比大小** |
| **量化部署**（<10MB / <100ms） | ✅ 真遇到且**失败** —— INT8 四档端到端检出**全为 0**，如实归档，不包装 |
| **空鼓/内部脱开**可见光下只能给间接迹象 | ✅ 提前声明边界：真正确认空鼓要靠敲击法或红外热成像 |
| **时间与算力** | ✅ 真遇到。用早停（patience=25）与分档对照控制训练成本 |

**（3）一句话收尾**

> 「预期里最难的一条不是精度，是**敢不敢承认自己判不了**。
> 我们把这条做成了系统的第一等公民 —— 所以最终的困难不是技术上的，
> 而是**克制住"总得给个结论"的冲动**。」
