# 掉帧治理 · 实测定位与提速结论

> **目标**：让掉帧情况消失。
> **结论先行**：**没有掉帧 —— 是被人为节流。** 唯一收益最大的改动是把推帧间隔
> 从 300ms 放开到 100ms，实测端到端 **2.24 → 9.50 fps（+4.2 倍）**。
> 分析时间：2026-09-27。所有数字均来自本机实测脚本，非估算。

---

## 一、结论先行

| 项 | 改动前 | 改动后 |
|---|---|---|
| **端到端帧率** | 2.24 fps（压测）/ 3.33 fps（真机录屏） | **9.50 ~ 9.77 fps** |
| 服务端单帧能力 | 24.4 fps（p50） | 同（未变） |
| 能力利用率 | **9%** | **39%** |
| 屏幕 fps 数字 | 服务端 `0.01`（低报 300×）、前端 `3.1`（锁死） | 服务端 `7.03`、前端 `9.3`（偏差 2.1%） |
| 丢帧可观测性 | 无 | 有 `dropped` 计数 |

**判断依据**：三层实测（见下）一致指向同一个瓶颈 —— **`INTERVAL = 300ms` 这个上游闸门**。

---

## 二、三层实测：瓶颈到底在哪

### 第 1 层：服务端单帧能力（`logs/_measure_pipeline_stages.py`）

| 阶段 | p50 | 占比 |
|---|---|---|
| ① JPEG 解码 | 2.1 ms | 5.2% |
| **② 模型推理** | **37.4 ms** | **91.2%** |
| ③ draw_overlay | 0.7 ms | 1.8% |
| ④ JPEG 编码 | 1.2 ms | 3.0% |
| **合计（串行）** | **41.0 ms** | 100% |

**⇒ 串行上限 = 24.4 fps（p50）/ 15.3 fps（p99）。**

> 注意：另一轮用 448×448 小图测出 17.6 ms，比这低一半。
> 差异来源 = **手机推上来的 960×720 大图在 `run_one` 内要缩到 imgsz 640**，
> 大图缩放更贵。**所以不能拿小图耗时估算真机能力** —— 必须用推帧尺寸。

### 第 2 层：端到端能力扫描（`logs/_bench_interval_sweep.py`）

| INTERVAL | 目标 fps | **实测端到端** | 达成率 | 推帧错误 |
|---|---|---|---|---|
| **300**（原默认） | 3.33 | **2.24** | **67.3%** | 0 |
| 200 | 5.00 | 4.98 | 99.6% | 0 |
| **100**（新默认） | 10.00 | **10.06** | **100.6%** | 0 |
| 66 | 15.15 | 15.15 | 100.0% | 0 |

**两个反直觉发现**：

1. **300ms 是唯一"不达标"的档位（67.3%）** —— 不但最慢，还是唯一不合格的。
   判断是 `setInterval` 固定节奏与识别周期（~41ms）**节拍共振**导致丢拍；
2. **提速到 15fps 依然 100% 达成、零错误** —— 服务端完全扛得住，还有余量。

### 第 3 层：浏览器内推帧各段耗时（`logs/_profile_push_stages.py`）

在真实浏览器里（Playwright + 假摄像头）逐段计时：

| 环节 | p50 | p95 |
|---|---|---|
| A. `drawImage` | 1.4 ms | 3.7 ms |
| B. `toBlob`（JPEG 编码） | **2.0 ms** | 8.6 ms |
| C. `fetch('/push')` | **2.1 ms** | 3.0 ms |
| **A+B+C 合计** | **5.7 ms** | 14.5 ms |

**⇒ 手机端推帧上限 175 fps，完全不构成瓶颈。**
同时测得：**摄像头源头 20.1 fps，分辨率 1280×720**。

**三层对照**：

```
摄像头源头 20.1 fps  ──┐
手机推帧   175   fps  ──┼──▶  服务端能力 24.4 fps  ──▶  实际 3.33 fps
网络        500  fps  ──┘                                    ↑
                                                    ★ 瓶颈只在这里：300ms 闸门
```

## 三、收益最大的改动

### ① 打开闸门：`INTERVAL` 300 → 100（核心改动）

- 实测收益：**2.24 → 9.50 fps（+4.2 倍）**；
- 为什么是 100 而不是 66：100ms 已达 100.6% 达成率，且服务端串行上限 24.4 fps，
  100ms 留了近 2.5 倍余量；66ms 收益有限但推帧量与带宽翻倍；
- 已抽成模块级常量 `DEFAULT_INTERVAL_MS`（单一真源）。

### ② `setInterval` → 自适应 `setTimeout`（防塌陷）

**为什么必需**：`setInterval` 是固定节奏，若某拍耗时超过 `INTERVAL`，
下一次回调立刻触发而 `pushing` 正为真 ⇒ **那一拍被静默丢弃**，
既无计数、也无法区分「没发」与「发了被丢」。
300ms 档只达成 67.3%，正是这个机制。

改为「推完一帧（含 fetch 往返）再排下一帧」：

- 队列里**永远只有 1 帧在途**，不堆积、不雪崩；
- 节奏自适应实际链路速度，慢的时候自动降频而非丢帧；
- 记 `dropped`，把「来不及」变成**可观测数字**。

### ③ fps 显示口径修正（从"死数"变"真值"）

两处都是**累计平均冒充瞬时值**：

| 位置 | 旧实现 | 问题 | 新实现 |
|---|---|---|---|
| `phone_live.py` `logStat()` | `sent/(now-t0)`，`t0` 只设一次 | 锁死成 3.1，看不出波动 | 自上次采样的增量 |
| `live_stream.py` `StreamState.fps` | `_frames/(now-_t0)`，`_t0` 只在 reset 更新 | 低报 300×（显示 0.01） | 3 秒滑动窗口 |

> 这两个不是"加功能"，是**修 bug** —— 屏幕上的数字此前是错的。

## 四、过程中的两个坑（值得记录）

### 坑 1：默认值分叉，导致"改了一处却没生效"

`interval_ms` 的默认值**曾在两处各写一份**：

- `main()` 里 `_arg("interval", "100")`
- `build_app(..., interval_ms: int = 300)`

我改了 `main` 却没改 `build_app`。而验证脚本调用 `build_app(args, quality=...)`
**不传 `interval_ms`** ⇒ 拿到 300 ⇒ 实测仍是 3.24 fps，**一度误判成"改动无效"**。
运行时诊断（`logs/_diag_loop_runtime.py`）打出 `"intervalVal": 300` 才定位到。

**修法**：抽成模块级 `DEFAULT_INTERVAL_MS`，两处都引用它，并加回归断言。

### 坑 2：滑动窗口的停帧边界

第一版滑动窗口在"窗口内样本 < 2 点"时退回取最后两个样本硬算，
结果**停帧 3.2 秒后仍显示 39.21 fps**（应为 0）。
**修法**：先判断最后一帧距今是否超出窗口，超出即返回 0。

> 这两个坑都不是靠读代码发现的，是**靠断言失败**发现的 —— 印证「必须真跑」。

## 六、还没做的事（诚实边界）

1. **未在真机复测**。所有 9.5 fps 是**本机环回 + 假摄像头**测的。
   真机的摄像头、WiFi、手机 CPU 都可能改变结论 —— 建议按同法在真机复测一次；
2. **`dropped` 显示逻辑未在真机验证**：为 0 时不显示，
   真机若出现负数或异常值需回看；
3. **imgsz / 输出宽度未动**：若真机上 9.5 fps 仍不够，
   下一步应降 `out_w`（960→720）或 `imgsz`，实测过 448 图仅 17.6ms、有翻倍空间；
4. **`_verify_phone_fullscreen.py` 本轮未跑通**（它需要外部 https 服务，
   走代理报 502），全屏 UI 的回归覆盖改由本轮浏览器验证承担。
