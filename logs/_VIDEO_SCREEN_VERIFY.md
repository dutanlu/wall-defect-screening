## 三、跑通过程中发现并修复的 3 个真实缺陷

这三个都是**实跑才暴露**的，静态检查（`py_compile`）全部通过。

### 缺陷 1：`conf_median` 恒为 0.000

**现象**：聚合后的置信度全部是 0，导致「代表帧」无法按置信度挑选。

**根因**：`pipeline.run_one` 输出的 `measurements` 用的是
`Measurement.to_dict()`，而它走 `asdict()`，**只序列化 dataclass 声明字段**。
`conf` 是运行时塞进 `m.__dict__` 的额外字段 ⇒ 不输出。

（`app.py` 的 payload 早就有这个处理并写了注释，`pipeline.py` 漏了。）

**修法**：`pipeline.py` 输出时显式合并 conf（与 `app.py` 同口径）。

### 缺陷 2：`consistent` 判定恒为 False（量纲错误）

**现象**：`crack` 的 CV 只有 9.3%，却判「帧间不一致」。

**根因**：
```python
"consistent": bool(w_cv <= CV_INCONSISTENT),
```
`w_cv` 是**百分数**（4.6 表示 4.6%），`CV_INCONSISTENT` 是**小数**（0.35）。
`4.6 <= 0.35` 恒为 False ⇒ **所有轨迹都被误判为不一致**。

**修法**：`bool(w_cv <= CV_INCONSISTENT * 100)`。

**验证**（单测）：
| 输入宽度序列 | CV | consistent |
|---|---:|---|
| [54.0, 57.0, 60.5] | 4.6% | **True** |
| [10.0, 50.0, 90.0] | 65.3% | **False** |

### 缺陷 3：逐帧独立标定严重不稳定（★ 最重要的发现）

**现象**：同一段 1.33 秒、同一面墙的视频，逐帧做砖缝周期标定得到的 GSD：

| 抽帧间隔 | 各帧 GSD (mm/px) | 极差 |
|---|---|---:|
| every=0.5s（4 帧） | 21.28 / 13.03 / 12.34 / 22.27 | **80%** |
| every=0.3s（5 帧） | 21.28 / 20.39 / 28.84 / 19.44 / 21.88 | **42%** |
| every=0.5s（4 帧，复核跑） | 21.28 / 13.03 / 12.34 / 22.27 | **57.6%** |

> 第三行是 2026-09-25 13:10 用 `--every=0.5 --max-frames=6` 复核的输出
> （实际抽到 4 帧、极差按 max/min 与中位数算得 57.6%），与第一行同源、数量级一致。
> 复核命令：
> ```
> cd 02_code
> D:\下载\python.exe -X utf8 video_screen.py ^
>   --video=../logs/_test_video/synthetic_wall_walk.mp4 ^
>   --model=../weights/v11s640_best.pt ^
>   --every=0.5 --max-frames=6 --device=cpu --calib-brick ^
>   --json=../logs/_video_verify_out.json
> ```
> 告警原文（已自动写入 JSON 的 `summary.calibration_stability.warning`）：
> 「逐帧 GSD 极差达 57.6%（超过 20%）⇒ **逐帧标定不稳定**……
> 建议以 gsd_median 作为本段视频的统一尺度重算」。

**根因**：砖缝周期检测对画面平移/裁剪敏感，而视频帧间必然有位移。

**后果有多严重**：GSD 直接决定毫米数。若逐帧各用自己的 GSD，
同一处缺陷在不同帧上会被量成差 80% 的宽度，而「跨帧取中位数」
会把这种**系统性偏差平均掉**，产生一个「看似稳定、实则无意义」的数字。

**修法**：`video_screen.py` 的 `summarize()` 新增
`calibration_stability` 诊断块 —— 汇总各帧 GSD、给出中位数与极差，
**极差 > 20% 时显式告警**，并建议以中位数作为本段视频的统一尺度重算。

> ⚠️ 本修法**只做诊断与报告，不改各帧已算出的测量值**
> （遵守「不改动已上报数字」的纪律）。若要按统一 GSD 重算，需显式重跑。

## 四、修复后的实测输出

### 标定稳定性诊断

```
逐帧 GSD: [21.2785, 20.3942, 28.8436, 19.4448, 21.8789]
中位 GSD = 21.2785 mm/px
极差     = 42.0%
stable   = False
methods  = ['brick_period']
```

### 跨帧稳定轨迹（n_frames ≥ 2）

| 类 | 帧数 | conf 中位 | conf 最高 | 宽中位 (mm) | 宽 CV | 一致 |
|---|---:|---:|---:|---:|---:|---|
| crack | 5 | 0.445 | 0.519 | 82.95 | 7.8% | ✅ |
| spalling | 3 | 0.752 | 0.797 | 0.00 | 0.0% | ✅ |
| crack | 2 | 0.593 | 0.708 | 115.13 | 2.5% | ✅ |
| crack | 2 | 0.450 | 0.626 | 89.01 | 11.5% | ✅ |
| crack | 2 | 0.386 | 0.467 | 96.03 | 8.4% | ✅ |

### ★ 一个正面结论

**跨帧测量的复现性很好**：5 条稳定轨迹的宽度 CV 在 **2.5% ~ 11.5%**。
这说明「检测 + 分割 + 测量」这条链路的跨帧一致性是可靠的 ——
**真正的问题在标定（GSD），不在测量本身**。

这个结论对改进方向有直接指导意义：
要让视频的毫米数可信，应当解决**标定**，而不是去改测量算法。

## 五、功能边界（必须与功能一起交付）

| 能做到 | 不能做到 |
|---|---|
| 接受 mp4/avi/mov/mkv 等视频输入 | **不能提高毫米级判读能力** |
| 按时间等间隔抽帧（`--every` 秒） | 不能替代实拍的高分辨率照片 |
| 复用现有单图管线（检测/量化/分级） | 不能自动跟踪快速运动目标（用贪心匹配，非 SORT） |
| 跨帧聚合同一缺陷（中心距 / IoU 匹配） | 不能消除逐帧标定抖动（只能诊断并告警） |
| 逐缺陷报「跨帧中位数」+ 离散度 | **未在真实拍摄视频上验证** |

### 写进 JSON 的诚实约束（下游无法忽略）

`capability_note` 字段原文：

> **视频不提高毫米级判读能力。** 判读门槛由 GSD 决定，而 GSD 只取决于
> 镜头物理分辨率与拍摄距离 —— 一帧 1080p 视频帧与一张 1080p 照片的
> 判读能力相同。视频的价值在于覆盖面（一圈墙 vs 一张照片）与多视角
> 冗余（减少漏检），不改变 0.3mm 裂缝能否判读。逐缺陷的毫米值为
> **跨帧中位数**，单帧值不单独采信（见 width_cv_pct）。
> ★ 另需注意：**逐帧独立标定不稳定**（实测极差可达 80%），
> 因为砖缝周期等标定方式对帧间位移敏感。同一段视频应只有一个 GSD，
> 见 calibration_stability。
