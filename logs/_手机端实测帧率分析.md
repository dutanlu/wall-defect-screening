# 手机端实时链路 · 实测数据分析

> **数据来源**：用户真机录屏 `13677a7cdda337f2be1215d091486fdf.mp4`
> （21.06 s / 576×1280 / HEVC / 24 fps，微信导出）。
> 抽帧口径：`fps=2` 抽帧 + HUD 区域裁切放大逐帧读数。
> 分析时间：2026-09-27。**本文所有数字均从录屏画面读出，非估算。**

---

## 结论先行（TL;DR）

1. **实测端到端结果帧率 = 3.33 fps**（12.0 s 内 `已推理 111 → 151`，共 40 帧）。
2. **屏幕上的两个 fps 数字都是错的**，且**错的方向相反**：
   - 服务端显示 **`0.01 帧/秒`**（全程几乎不变，12s 处才跳到 0.02）→ **低报约 300 倍**；
   - 手机端显示 **`3.1 帧/秒`**（全程锁死在 3.1）→ 相对真值 3.33 **低报约 7%**，但**它是死数**，看不出任何波动。
   - **真值 3.33 恰好落在 3.1 和 0.01 之间，且离 3.1 近得多** ⇒ 手机端那个数虽口径错，数量级是对的；服务端那个数**完全不可用**。
3. **帧率抖动严重**：区间帧率在 **2.0 ~ 5.0 fps** 之间摆动，std = 1.20，**极差 3.0 fps（峰谷比 2.5×）**。
4. **真正该看的不是"平均值"，而是"抖动"和"低报口径"** —— 前者影响判读可用性，后者让你对系统状态完全失去感知。
5. **综合最优方案与最低开销方案在架构上并不冲突**：最低开销 = 服务端 `seq` 差分（零手机负担），最优效果 = 同一份数据的滑动窗口统计。**推荐直接用后者，它同时满足两端。**

## 二、综合效果最好的方案

**判定：服务端 `seq` 差分 + 滑动窗口统计。**

### 判断依据

1. **唯一零偏差**：`Δseq/Δt` 直接来自服务端单调递增的 `seq`，它就是端到端结果帧率本身，不存在"用累计值冒充瞬时值"的口径损失。实测整段 3.333 fps，这个数只有它算得出来。
2. **唯一能反映抖动**：本轮实测的 2.0 / 4.0 / 5.0 fps 波动，前端（3.1 锁死）和服务端（0.01 锁死）**都看不见**。而抖动恰恰是判读可用性的决定因素 —— "对着墙慢慢扫"时，扫过的那几帧若正好落在 2.0 fps 的低谷，就可能漏检。
3. **口径唯一、不依赖手机**：手机端算的任何数都被手机自身负载污染（手机越忙、越可能漏算）。服务端 `seq` 是**推理线程真实产出**，不受手机负载影响。

### 关键数据

- 真值 **3.333 fps** vs 显示 `3.1`（−7%）vs 显示 `0.01`（−99.7%）；
- **抖动 std 1.200 / 极差 3.000**：这是任何"平均值口径"都必然丢失的信息。

## 三、开销最低的方案

**判定：服务端 `seq` 差分。**

### 量化依据

| 开销项 | 前端 `logStat()` | 服务端 `STATE.fps` | **`seq` 差分（推荐）** |
|---|---|---|---|
| 手机 CPU | 每次推帧 1 次除法 + 1 次 DOM 写 | 0 | **每秒 1 次 JSON 解析** |
| 手机网络 | 0 | 0 | **1 次 GET /status，约几百字节/秒** |
| 手机内存 | 0 | 0 | 0（复用已有 `lastSeq/lastT` 两个变量） |
| 服务端 CPU | 0 | ~1 次属性读 | 0（`seq` 已在 `/status` 里） |
| **是否引入新定时器** | 否（搭在 push 回调） | 否 | **否（复用已有 1500ms 轮询）** |

**结论**：`seq` 差分**不增加任何新的采集机制** —— 它复用了手机页里**已经存在的** 1500ms `/status` 轮询。端点、字段、轮询节奏全部现成，只改**怎么用这几个数**。因此它的边际开销 ≈ **0**，比"新增 rVFC 探针"还低。

> ⚠️ 更关键的一点：**当前的两个显示值本身就消耗了资源却给出错误信息**。改成 `seq` 差分不仅不加开销，反而**让已有开销产出正确结果** —— 这是纯收益。

---

## 四、权衡结论与最终推荐

**效果最优（seq 差分 + 滑动窗口）与开销最低（seq 差分）是同一方案的不同深度** —— 数据结构完全相同，区别只在于**聚合时算不算 p95/std**。因此**不存在真正的二选一冲突**。

### 最终推荐

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| **正式演示（答辩/交付）** | **`seq` 差分，1s 窗口，只显示瞬时 fps** | 零额外开销，数字唯一可信，评委问口径能一句话说清 |
| **正式但需稳定性证据** | 上述 + **同时显示 1s 瞬时值 + 10s 窗口均值** | 两个数并列，抖动一眼可见，仍无额外开销 |
| **真机问题排查（临时）** | 上述 + `rVFC` 源头帧率 + `PerformanceObserver(['longtask'])`，**`?debug=1` 才开** | 区分"摄像头源头卡"vs"识别/网络卡" |
| **绝不要** | 在正式环境常开逐帧时间戳/console 日志/GPU 深挖 | 测量本身会掉帧 |

### 各自适用条件

- `seq` 差分**要求服务端持续产出 `seq`**——本项目已满足（`/status` 返回 `seq`、`n_received`、`n_inferred`）；
- 若某天链路改成**无服务端**（纯端侧推理），`seq` 差分失效，退化为 `rVFC` 源头帧率 + `requestIdleCallback` 兜底；
- **本轮实测环境下（手机 + 同一 WiFi + 本机推理），`seq` 差分是最优解**，因为它把"手机负载"这个最大噪声源完全排除在外。

## 五、针对当前瓶颈的可落地优化

### 瓶颈定位（按影响排序）

**瓶颈 1：口径错误 —— 已实测确认，且正在误导判断**

- 服务端 `0.01 fps` 与真值差 **300 倍**。任何看这个数的人都会以为链路基本没在工作；
- 根因（代码已定位）：`live_stream.py` 的 `StreamState.fps` 用 `self._frames / (time.time() - self._t0)`，`_t0` 只在 `reset()` 时更新 ⇒ **累计平均**。当 `seq` 已到 151 但 `_frames` 计数与时间基线不匹配时，得出 0.01 这种荒谬值；
- **修法**：改为滑动窗口（保留最近 N 个 `(t, seq)` 样本）。

**瓶颈 2：前端显示是死数 —— 无法感知波动**

- 根因：`phone_live.py` 的 `logStat()` 用 `t0`（`begin()` 时设定，之后不重置）；
- **修法**：每次 `logStat` 后重置基线，或直接改用 `/status` 的 `seq` 差分。

**瓶颈 3：抖动 1.20 std / 3.0 极差**

- 可能来源（需下一步验证）：
  1. **摄像头输出本身不稳**（请求 1280×720，真机可能给不出稳定 720p）；
  2. **`INTERVAL` 与识别耗时（60–200ms）不匹配** —— 实测 3.33 fps ⇒ 帧间隔约 300ms，**高于**识别耗时上限 200ms，说明瓶颈**可能不在识别**，而在采集或推帧；
  3. **`pushing` 背压丢帧**：`pushOne()` 在 `pushing=true` 时直接 return，**被挡掉的帧静默丢弃**，无计数 ⇒ 无法区分"没发"和"发了被丢"。

- **修法**：加一个 `dropped` 计数器（`pushing` 挡住时 +1），与 `sent` 一起上报。这一个数字就能定位抖动来源。

**瓶颈 4：缺少分层速率，无法二分定位**

- 当前只能看到端到端。建议补 **`rVFC` 源头帧率**，与端到端并列显示。两者一对比：
  - 源头也低 ⇒ 摄像头/采集问题；
  - 源头正常、端到端低 ⇒ 推帧/网络/识别问题。

### 优化优先级（建议按序落地）

| 优先级 | 动作 | 预期收益 | 改动量 |
|---|---|---|---|
| **P0** | 修 `STATE.fps` 为滑动窗口 | 消除 300× 误报 | 小 |
| **P0** | 前端改用 `seq` 差分 | 数字从"死数"变"真值" | 小 |
| **P1** | 加 `dropped` 计数 | 定位抖动来源 | 极小 |
| **P2** | 加 `rVFC` 源头帧率 | 分层二分定位 | 中 |
| **P3** | `?debug=1` 才开长任务探针 | 排查期用，正式关闭 | 中 |

> **注意**：P0/P1 会改动可见界面，按项目纪律需**连带走重录演示视频**流程。
