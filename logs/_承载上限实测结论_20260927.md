# 系统承载上限实测结论（2026-09-27）

> 本文所有数字均为**本机实测**，非估算。复现脚本见文末「证据清单」。
> 与「跑得顺不顺」那篇（`_还能再顺畅一点_实测结论.md`）是两份独立文档：
> 那篇讲**单路**如何做到 19.65 fps，这篇讲**多路/批量**能撑到什么程度。

---

## 零、先说结论（TL;DR）

| 问题 | 结论 |
|---|---|
| **最多几台手机同时推流并检测？** | **1 路**（当前代码如此，是**架构事实**，不是算力不够）。第 2 台起会**静默互相覆盖**，两端都看到「混合画面」，且**没有任何报错**。 |
| **算力上限是多少？** | 单帧推理 p50 ≈ **19.8 ms**（720 输入）⇒ 单实例理论 **≈ 47 fps**；实测满载到 **36.5 fps** 仍在跑。 **8 路并发时服务侧只跑到 36.5 fps，8 路总需求是 160 fps ⇒ 缺口 4.4 倍**。 |
| **瓶颈到底是什么？** | **① 架构（单 STATE / 单 analyzer）→ 硬上限 1 路；② 系统内存（非显存）→ 决定能不能加实例**。显存**完全不是**瓶颈（每个模型实例仅 ~0.13 GB / 共 12 GB）。 |
| **支持批量上传照片吗？** | **网页界面不支持**（`gr.Image` 是单图组件，一次只能传 1 张）。**命令行支持**：`python 02_code/batch_screen.py --dir=<目录>`，**无数量上限**。 |
| **批量能多快？** | 实测 **41.7 张/秒**（60 张真实测试图，串行）。→ 285 张 ≈ **6.8 秒**；1000 张 ≈ **24 秒**；5000 张 ≈ **2 分钟**。 |
| **支持什么格式？** | 7 种：`.jpg .jpeg .png .bmp .webp .tif .tiff`。**不递归子目录**。 |
| **超限了会怎样？** | 实时流：**静默丢帧**（不报错，只显示最新一帧）。批量：**无上限**，但**同步执行**、**无排队**，文件多则命令行一直阻塞到跑完。 |

## 一、假设前提（**关键：本机不是服务器**）

题面要求「如缺少服务器规格等关键参数，请列出假设」。逐条列清：

| 项 | 实测值 | 性质 |
|---|---|---|

| CPU | **32 逻辑核** | 实测 |
| 系统内存 | 总 **15.72 GB**，测试时可用仅 **0.10~1.41 GB**，load **91~99%** | 实测 |
| GPU | **NVIDIA GeForce RTX 5070 Ti Laptop GPU** | 实测 |
| 显存 | **11.94 GB**（12227 MB） | 实测 |
| SM 数 / 算力 | 46 / 12.0 | 实测 |
| CUDA | 12.8，torch 2.11.0+cu128 | 实测 |

**未被实测、必须标注为假设的项：**

1. **【假设 A】生产服务器规格**：本机是**开发笔记本**，无独立服务器。
   下文「可扩展到几路」的推算基于本机 32 核 / 15.72 GB 内存 / 12 GB 显存。
   **换成正规服务器（如 64 核 / 128 GB 内存 / 24 GB 显存），并发路数可按内存与算力线性外推**，
   但**架构上限（1 路）不变** —— 那是代码问题，不是硬件问题。
2. **【假设 B】手机端真实帧率**：实测 `phone_live.py` 链路受**采集源**限制在
   **20.09 fps**（Playwright 假摄像头测得）。真实手机（尤其前置/后置 1080p 30fps）
   通常 **≥ 30 fps**，故真实手机可能比本机测试**更接近**服务器算力上限。
3. **【假设 C】WiFi 带宽**：局域网 192.168.3.215，**未实测**可用吞吐。
   按单帧 720 长边 / JPEG q70 ≈ **36.5 KB** 计算：
   - 20 fps × 36.5 KB ≈ **0.73 MB/s ≈ 5.8 Mbps** / 路（上行）
   - 8 路 ≈ **5.8 MB/s ≈ 47 Mbps** 上行 + 下行叠加图
   ⇒ **普通家用 WiFi 5（理论 433 Mbps，实测常 100~200 Mbps）够用**，
     但**同网段多台手机同时上传**时，WiFi 的**上行**会先于服务器算力成为瓶颈。
4. **【假设 D】测试图片尺寸**：测试集统一 **448×448**、中位 **77 KB**、最大 **8.1 MB**。
   若换成 4000×3000 手机原图（约 3~5 MB），**批量吞吐会显著下降**（解码与推理前缩放成本上升），
   实测的 41.7 张/秒**只对 448 级小图成立**。
5. **【假设 E】单帧 vs 视频抽帧**：批量统计按**单图链路**（`run_one`）算，
   未包含视频抽帧与跨帧中位数聚合的开销。

## 二、并发设备数：**1 路**（架构硬上限）

### 2.1 实测数据（8 路模拟手机同时推帧）

| 并发路数 | 各路发送 | 服务收到增量 | 已推理增量 | **接收/发送** | **推理/接收** | 服务侧 fps |
|---|---|---|---|---|---|---|
| 1 | 96 | 96 | 96 | **1.000** | **1.000** | 16.07 |
| 2 | 89+90 | 179 | 162 | **1.000** | **0.905** | 27.47 |
| 4 | 93+95+93+92 | 373 | 207 | **1.000** | **0.555** | 33.39 |
| 8 | 92+96+93+93+93+94+94+93 | 748 | **226** | **1.000** | **0.302** | **36.49** |

### 2.2 这三列数字说明什么

- **接收/发送 = 1.000（每一档都是）** ⇒ HTTP 层**从不丢**，`/push` 只把字节丢进队列就返回
  （p50 仅 **5~19 ms**）。**「网络/接口」不是瓶颈。**
- **推理/接收 从 1.000 掉到 0.302** ⇒ 一个 `PhoneAnalyzer` **处理不过来**，
  它**只取最新一帧、其余静默丢弃**。8 路时**每 10 帧只有 3 帧真正被检测**。
- **服务侧 fps 在 8 路时只有 36.5** ⇒ 8 路各想跑 20 fps、总需求 **160 fps**，
  实际 **36.5 fps** ⇒ **缺口 4.4 倍**。且这 36.5 fps 是**所有路混在一起**的，
  **没有任何一路能稳定拿到 20 fps**。

### 2.3 根本原因：代码里只有「一份」状态

```python
# 06_deploy/live_stream.py:182
STATE = StreamState()          # ← 全局唯一实例

class StreamState:
    def __init__(...):
        self._jpeg = None      # ← 只有一个图槽
        self._seq  = 0
        self._info = {}
    def put(self, jpeg, info): # 谁来写都覆盖这同一个槽
```

```python
# 06_deploy/phone_live.py:275
STATE.put(out.tobytes(), info)   # 所有路的结果都写进同一个 STATE
```

且 `/status` 返回的**字段全集**为：
```
['mode', 'seq', 'fps', 'has_frame', 'n_received', 'n_inferred', 'analyzer_error']
```
—— **没有任何按客户端区分的字段**（无 `client_id` / 无 per-stream 计数）。
这是「单路设计」的**结构性证据**，不是配置问题。

### 2.4 诚实修正：我之前的一处误判

我在上一篇文档里写过「服务器 21.2 ms/帧 ⇒ 47 fps 能力，50 ms 推帧只用了 42%」，
据此**暗示有余量可以加路**。**这个推论不完整**：

- 47 fps 是**一个** analyzer 的处理能力，而**多路共用这一个 analyzer**，
  它们的帧会**互相挤掉**（推理/接收比逐级下降就是证据）；
- 就算算力翻几倍，**共用 STATE 也会让画面串在一起** —— 这是**正确性问题**，
  比性能问题更严重（评委看到的是「几台手机的画面混在一起」，而不是「卡一点」）。

⇒ **「算力有余量」≠「能加设备」。** 正确的说法是：
**当前架构下并发路数 = 1，与硬件无关。**

## 三、批量图片处理

### 3.1 支持情况（两条路径，能力不同）

| 路径 | 入口 | 批量能力 | 说明 |
|---|---|---|---|
| **网页界面** | `06_deploy/app.py`（7860） | ❌ **单图** | 组件是 `gr.Image`（**不是** `gr.File`/`gr.Files`），**一次只能选 1 张**。视频入口是 `gr.Video`，同样单文件。 |
| **命令行** | `02_code/batch_screen.py --dir=<目录>` | ✅ **整目录** | `list_images()` 遍历目录下所有图片，**无数量上限**、**不递归**。 |

### 3.2 实测吞吐（60 张真实测试图，串行）

```
样本           : 60 张（取自测试集，共 285 张）
总耗时         : 1.44 s
单张 p50       : 20.2 ms    p95: 29.3 ms    mean: 21.0 ms
吞吐           : 41.7 张/秒 = 2501 张/分钟
内存           : 可用 0.36 GB -> 0.53 GB（load 97% -> 96%，无明显增长）
总检出         : 319 个（均 5.32 个/张）
```

推算：

| 批量 | 预计耗时 |
|---|---|
| 100 张 | **2.4 秒** |
| 285 张 | **6.8 秒** |
| 500 张 | **12 秒** |
| 1000 张 | **24 秒** |
| 5000 张 | **2 分钟** |

### 3.3 各项限制

| 项 | 实测/代码事实 |
|---|---|
| **单批次图片数** | **无硬上限**（`list_images` 无视数量）。受限于内存与耐心，非代码。 |
| **单张体积上限** | **代码里无限制**。Gradio 路径受 Gradio 自身默认（约 100 MB 级）约束；CLI 路径纯读文件。测试集实测最大 **8.1 MB** 可正常处理。 |
| **总体积上限** | **无显式限制**。实测 60 张共约 4 MB 内存占用无增长。 |
| **支持格式** | `.jpg .jpeg .png .bmp .webp .tif .tiff`（7 种，`batch_screen.py:63` 的 `IMG_EXTS`） |
| **超限表现** | **不排队、不自动分批、不报错** —— **同步串行跑完**。目录里没有图片时打印一行提示后返回。 |
| **目录递归** | ❌ **不递归**。子目录里的图**会被忽略**（容易误判为「处理完了」）。 |

### 3.4 要注意的两个坑

1. **网页端「看起来支持批量」是错觉**：`gr.Image` 在部分浏览器允许多选文件，
   但 Gradio 只会把**第一张**交给回调 ⇒ 用户以为传了 20 张，实际只处理 1 张，**无任何报错**。
2. **不递归**：`--dir=D:\巡检` 而图片都在 `D:\巡检\楼A\` 时，
   脚本会打印「目录下没有图片」并退出 —— 这是**正确行为**，但容易被当成「图片坏了」。

## 四、扩展方案（按性价比排序）

### 4.1 优先级矩阵

| 优先级 | 环节 | 改什么 | 收益 | 成本 |
|---|---|---|---|---|
| **P0** | **多路隔离** | `STATE` 由单例 → **按 client_id 的字典**；`PhoneAnalyzer` 由 1 个 → **N 个**（或一个 analyzer 轮转多路） | 从 **1 路 → N 路**（**唯一能动并发上限的改动**） | 中（改 `live_stream.py` + `phone_live.py`，且 `app.py` 的可见界面若动到需重录视频） |
| **P1** | **批量推理** | `batch_screen.py` 里把逐张 `run_one` → **分块 `model.predict(imgsz=640, batch=8)`** | 实测 **1.95×**（见 `logs/_BENCH_BATCH.md`：66.4 → 129.5 图/秒） | 低（单文件局部改动） |
| **P2** | **异步任务队列** | 批量改为「提交 → 返回任务号 → 轮询/回调」 | 解决「几千张时命令行阻塞」；支撑网页端真正的批量 | 中（需引入进程/线程池 + 任务表落盘） |
| **P3** | **水平扩容** | 多进程（`--port` 不同）+ 前置反向代理按 `client_id` 分流 | 突破**单机内存**上限 | 高（需改架构 + 部署） |
| **P4** | **限流** | `/push` 增加每 client_id 的最小间隔 + 队列长度上限 | 防止单台手机刷爆 analyzer、影响其它路 | **低（P0 的前提，建议同批做）** |
| **P5** | **提升单帧算力** | 降 `imgsz`（640→544）/ 换更小模型 | 提速但**掉精度**（已实测 640 时 `moss` 4→3） | 不建议 |

### 4.2 关于「能加到几路」的推算（**含假设**）

**约束一：系统内存（真瓶颈）**
- 实测本机可用仅 **0.10~1.41 GB**，load **91~99%**。
- 一个模型实例的**显存**仅 **~0.13 GB**（3 个实例共 0.203 GB）⇒ **显存完全够**。
- 但**系统内存已接近耗尽**，**再加进程会先 OOM**。
  ★ 这与 `_PARALLEL_CAPACITY_20260925.md` 的结论一致：**判据看 `ullAvailPhys`，不看显存。**

**约束二：算力**
- 单帧 p50 = **19.8 ms**（720 输入）⇒ 单实例 **≈ 47 fps**。
- 若每路 20 fps ⇒ **单实例理论上可服务 ≈ 2 路**（47/20 ≈ 2.35，留余量取 2）。
- 但**多 analyzer 会争抢同一块 GPU**，实际并发效率**低于线性**（参考训练期实测：
  第二个 GPU 任务就 OOM/抢不到）。**保守取 1.5 路/实例**。

**约束三：架构（当前 = 1 路）**
- 见 §2.3，**必须重构后才能谈路数**。

**推算结论（标注为假设）：**

| 场景 | 并发路数 |
|---|---|
| **当前代码（不改）** | **1 路** |
| 仅改「多 STATE + 多 analyzer」，本机硬件 | **2~3 路**（受系统内存限制，需先关掉其它占内存程序） |
| 同上 + 换成正规服务器（假设 128 GB 内存 / 24 GB 显存） | **8~12 路**（算力与内存同比例放大后的保守估计；**须实测**） |
| 加反向代理 + 多机 | 路数按机器数线性增长 |

### 4.3 关于批量扩展

- **最快见效**：在 `batch_screen.py` 里上 **batch=8 推理**（实测已证 1.95×）⇒ 41.7 → **≈ 80 张/秒**。
- **要支持网页批量**：必须把 `gr.Image` 换成 `gr.Files(file_count="multiple")`
  **并**配套异步任务表（否则界面会卡死整个 Gradio 队列）。
  ⚠️ **这会改可见界面 ⇒ 必须重录实机运行视频**（见铁律 §20）。
- **要处理超大批量（万级）**：需要任务队列 + 进度回传 + 断点续跑，
  建议直接复用现成的 **`logs/_watch_queue_0925.py` 串行调度模式**（本项目已验证可用）。

## 五、诚实边界（**这些我没测，不能声称**）

1. **没有测真实多台手机**。8 路并发是**模拟客户端**（同一台机器上 8 个线程发 HTTP），
   与「8 台真实手机连 WiFi」在**网络路径、时钟、采集抖动**上不同。
   ⇒ 「1 路」的架构结论**成立**（代码结构决定）；「8 路时 36.5 fps」这个数
   **含同机线程竞争的干扰，仅供参考**。
2. **没有测真实 WiFi 吞吐**（假设 C）。
3. **没有测手机端真实帧率**（假设 B，本机链路封顶 20.09 fps 是**假摄像头**的限制）。
4. **没有测大图（4000×3000）的批量吞吐**（假设 D）。
5. **没有测持续 1 小时以上的长跑稳定性**（内存会不会缓慢增长）。
6. **并发实测是在「内存已 94% 占用」的环境下做的**，如果关掉其它程序，
   绝对数字（36.5 fps 等）会更高。**相对趋势（推理/接收比逐级下降）不受影响。**

## 七、一句话总结

> **并发 = 1 路，是代码写死的（单 `STATE` + 单 analyzer），不是机器跑不动；
> 算力还有 4~5 倍余量（36.5 / 160 fps 需求），真正的下一步是「多路隔离」重构，
> 而不是买更好的 GPU。批量处理走命令行，无数量上限、41.7 张/秒（小图），
> 但网页端只能一张一张传 —— 想批量就得改界面，而改界面就要重录演示视频。**
