## 二、我一开始猜错了（这段比结论更重要）

用户追问「还能再顺畅一点」时，我手上有两份数据：

1. `_sweep_push_resolution.py`：把长边从 960 降到 720，
   推理 p50 **27.4 → 17.8 ms（−34.8%）**，而检出总数 71 → 72、
   逐类一个都没少（`crack` 33 个五次全同）。
2. `_measure_pipeline_stages.py`：960 输入单帧串行 41.0 ms。

⇒ 我据此判断「**降推帧分辨率**是收益最大的一项」，
   并把手机端推帧长边从 960 改成 720（`DEFAULT_PUSH_MAXW = 720`）。

**然后实测把我否掉了**：

```
_verify_push_maxw.py 第一版实测：9.63 fps（与改前 8.96 几乎无差别）
```

只快了 0.7 fps。**说明 720 那个改动对端到端几乎没用。**

继续追，发现两个更深的问题（都出在**我的测量脚本**上，不是被测对象）：

| # | 现象 | 真因 | 教训 |
|---|---|---|---|
| 1 | 验证脚本实测 8.64 / 9.80 fps，而另一脚本实测 19.7 fps | 验证脚本里**硬写了 `interval_ms=100`**（上一轮的旧默认），而新默认已是 50ms | 「默认值分叉」第二次踩坑，这次踩在**测试脚本**上 |
| 2 | 同端口连起两次服务后，`sent` 冻在 25、20 次采样全同值 | H 组服务只 `srv.should_exit=True`（异步关闭），没等它释放端口就起了 I 组；且**没调 `analyzer.stop()`**，识别线程与模型实例叠加抢 GPU | **测量装置污染了被测对象** |

第 2 条特别危险：它看起来完全像「改动无效 / 新默认没生效」，
差一点让我把**正确的改动回退掉**。

## 三、真正的瓶颈在哪（三层实测，逐层排除）

| 环节 | 实测值 | 数据源 | 是否瓶颈 |
|---|---|---|---|
| 浏览器 drawImage | 1.4 ms | `phone_push_profile.json` | 否 |
| 浏览器 toBlob(JPEG) | 2.0 ms（p95 8.6） | 同上 | 否 |
| 浏览器 fetch 往返（loopback） | 2.1 ms | 同上 | 否 |
| 服务端 decode | 0.7 ms | `phone_stage_breakdown.json` | 否 |
| 服务端 run_one（720 输入，有检出） | **19.8 ms** | 同上 | 部分 |
| 服务端 draw_overlay | 0.2 ms | 同上 | 否 |
| 服务端 imencode | 0.6 ms | 同上 | 否 |
| **推帧间隔 INTERVAL** | **100 ms（旧）** | `phone_live.py` | **★ 是** |
| 摄像头源帧率 | **20.09 fps** | `phone_push_profile.json` | **★ 是（真天花板）** |

⇒ **瓶颈不是算力，是「人为限速」。** 服务端有 47 fps 的能力（21.2 ms/帧），
   摄像头源有 20.09 fps，而旧配置只跑到 8.96 fps。

**为什么我原先的「串行模型」是错的**（这是本次最有价值的认知）：

我原来以为「推一帧的总耗时 = 客户端耗时 + 服务端识别耗时」，
所以 100ms + 41ms ⇒ 理论上限 7.1 fps，100ms 已接近够用。

错在：`PhoneAnalyzer` 是**独立线程**，按自己的节奏消费 `_pending` 里
**最新的一帧**；而客户端自适应循环只用 `performance.now()` 量
**自己这一拍**的耗时。两者**解耦** ⇒
服务端慢只会让它跳过中间帧，**不会拖慢推帧节奏**。

反证就在旧数据里：66ms 档目标 15.15 fps，实测也是 15.15（100% 达成）。
若真串行叠加 41ms，66ms 档最多只能到 9.3 fps。
**当时我把「100% 达成」读成「刚好够用」，其实是「链路根本没有串行瓶颈」。**

## 五、安全余量核算（为什么敢用 50ms，以及为什么不再往下）

**下界（服务端跟得上吗）**
服务端**有检出时**单帧 21.2 ms`phone_stage_breakdown.json` ⇒ 上限 47 fps。
50ms 档 19.66 fps 只占用 **42%** 吞吐 ⇒ 约 **2.4 倍余量**。
⚠️ 该 21.2 ms 是在**真实测试图**（几十个检出框）上测的；
假摄像头是彩色噪声、检出≈0 ⇒ 假摄像头那几档偏乐观。
**真机余量比 2.4 倍小，取 50ms（而不是 33ms）正是为了留这份余量。**

**上界（摄像头源帧率）**
实测 **20.09 fps**（`phone_push_profile.json`，1280×720 假摄像头）。
19.83 fps 已用掉源帧率的 **98.7%** ⇒
**再降 INTERVAL 不会更快**，只会让 `drawImage` 反复拿到同一帧（白推）。
**这才是真正的天花板。**

**回退条件**（写进代码注释与 `--help`）：
若真机上看到「丢 N」持续增长，或 `收到 / 已推理` 稳态比值 > 1.25
（`/status` 里有这两个数），说明该手机源帧率或 WiFi 更弱 ⇒
用 `--interval=66` 回退一档。

## 六、最终改动（三处，全部单一真源）

`06_deploy/phone_live.py`：

1. **`DEFAULT_INTERVAL_MS = 50`**（原 100）
   —— 模块级常量，`main()` 与 `build_app()` 都引用它，禁止字面量。
2. **`DEFAULT_PUSH_MAXW = 720`**（原 960，散落三处字面量）
   —— 新增模块级常量；`build_app(push_maxw=)`、`build_app(out_w=)`、
   `PhoneAnalyzer(out_w=)` **三处默认值全部引用它**；
   `out_w` 由 `_derive_out_w()` 联动推导（`out_w` 若大于帧长边会凭空放大，纯亏）。
   JS 侧 `var MAXW = __MAXW__` 由服务端注入，不写字面量。
3. **JS 的 `maxw` 改为引用注入的 `MAXW`**。

> 注：第 2 项对端到端只有 **+0.7 fps**（9.0 → 9.6 在当时口径下）。
> 它的价值在于**服务端单帧 −48%（40.8 → 21.2 ms）与 p95 −66%（73.1 → 24.7 ms）**
> —— 即「卡顿尖刺」大幅减少，且为将来更高帧率留了余量。
> **它不是我原先宣称的「收益最大项」，这一点必须如实说明。**

## 七之二、顺手修掉的两个「交付包」问题（与本轮改动无直接关系，但真踩到了）

### (1) ★★ 交付包一致性 PASS，但**包内根本起不来**

`_pack_vs_src.py` **每一轮都 PASS**（内容不同=0 / 包有源无=0），
可在**包目录内**实跑入口直接崩：

```
deploy/phone_live.py  → ModuleNotFoundError: No module named 'common'
```

根因：`phone_live.py` 与 `live_stream.py` 都写死 `_ROOT / "02_code"`，

| | 入口位置 | 代码目录 |
|---|---|---|
| 源目录 | `<root>/06_deploy/` | `<root>/02_code/` ✓ |
| 交付包 | `<pack>/deploy/` | `<pack>/code/` ✗ |

**这两个是早就进包的老文件，一直起不来**，而 md5 一致性核对
**天然看不见** —— 路径解析错**不改字节内容**。
⇒ 已改为「候选目录探测 + 全不存在则显式报错」，两个文件同因同修。

**闭环验证**（判据不是「文件都在」，是**真起得来**）：
源侧 `py_compile` OK → 重新同步进包 → **在包目录内**起 `phone_live.py`
（`/status` 200、页面 `INTERVAL = 50` / `MAXW = 720` 注入正确）→
**在包目录内**起 `live_stream.py`（正常加载包内 `weights/v11s640_best.pt`）。

### (2) ★ 备份文件漏进交付包（两条例行判据都覆盖不到）

`EXCLUDE_SUFFIX = {..., ".bak"}` 用的是 `Path.suffix`，
而本工程备份命名是 `.bak_<时间戳>` / `.bak_<主题>`
⇒ `suffix` 取到 `.bak_0927_interval`，**精确匹配一个都拦不住**。实测漏了 3 个：

```
deploy/live_stream.py.bak_0927_interval
deploy/phone_live.py.bak_0927_interval
results/quant/quant_report.json.bak_20260925_063250
```

★ `_pack_vs_src.py` **两条例行判据都覆盖不到**：它只比**同名文件**，
而这几个备份**源和包都有且 md5 一致** ⇒ 既不报「内容不同」也不报「包有源无」。
**只能靠人看目录发现。**

⇒ 修法：加按**文件名子串**排除（`.bak` / `.backup` / `~` / `.orig` / `.rej`），
单测 7/7 PASS；3 个文件**移到**
`种子杯项目报告/外墙缺陷筛查项目报告/_removed_from_pack_20260927/`（不删除）；
重同步后包内 `*bak*` 条目 = **0**。

### 交付包最终状态

- 文件数 **5959**（共用）+ 371.43 MB；
- `_pack_vs_src.py` ⇒ **✅ PASS**（内容不同=0 / 包有源无=0 / 需复核=0）；
- 包内 `*bak*` = **0**；
- 包内两个入口均**实跑通过**（P0 纪律）。

## 八、诚实边界（不得夸大的部分）

1. **全部数据来自假摄像头（Playwright）+ 本机 loopback**，
   **不是**真机实测。真机的摄像头源帧率、WiFi 往返、手机编码能力都更弱
   ⇒ 真机大概率**低于** 19.83 fps。请用户真机复测后再定稿报告数字。
2. **真机对着墙时服务端单帧更重**（21.2 ms 那一档才是接近真机的），
   余量比 2.4 倍小；已用「取 50 而非 33」留出这份余量。
3. **本工程内无真实外墙巡检实拍** ⇒ 链路可用性在**合成流/假摄像头**上自检，
   **不代表已在实拍上验证**（与全线其它入口同一口径声明）。
4. 降推帧分辨率到 720 的**精度代价**：测试集上检出 71 → 72、逐类不减
   （`phone_resolution_sweep.json`）；但**测试集 ≠ 真实墙面**，
   小裂缝在真机上是否受影响**未验证**。这也是**没有**进一步降到 640 的原因
   （640 档 `moss` 从 4 → 3，测试集仅 4 个样本，−25%）。
5. 「更顺畅」的**体感**上限受**摄像头源帧率 20 fps** 约束 ——
   这已经不是软件能改的了，要更高只能换设备/降采集分辨率。
6. **只要动了 `phone_live.py` 的可见界面（含只改一句文案），
   就必须重录实机运行视频**（交付物 ③）。本次改了 `--help` 文案与启动打印，
   **故现行成片已过期，待重录。**
