# §5.1 露筋被归入「线状类」的定性实验与修复依据（2026-09-25）

**状态**：**已解决**（本轮实测确认 → 给出修复 → 已实现并回归）
**相关代码**：`02_code/grade.py`（`LINE_CLASSES` / `classify_unjudgeable`）
**证据**：`logs/_rebar_probe/probe.out`、`logs/_rebar_probe/probe2.out`

---

## 一、问题陈述

`grade.py` 里：

```python
LINE_CLASSES = ("crack", "exposed_rebar", "rust")
```

`classify_unjudgeable()` 对线状类走 **`crack_0.3mm` 判据**
（`interp_crack.level != "measurement"` ⇒ 弃权），对块状类走 **`blob_10mm`**。

**假设**：露筋（exposed_rebar）是**暴露的粗钢筋 / 锈胀条带**，其有意义的尺寸
**不是「发丝级裂缝宽度」**。把它按 0.3mm 判据把关，会导致该类**永远判不了**。

---

## 二、第一次探针：结论**不成立为「bug」**

`logs/_probe_rebar_lineclass.py`，默认 `--distance=20`，抽样 40 张：

```
类别              测量数   弃权数   弃权率
crack                3       3    100.0%
spalling             1       1    100.0%
efflorescence       28      28    100.0%
exposed_rebar       21      21    100.0%
rust               156     156    100.0%
delamination        10      10    100.0%
moss                 7       7    100.0%
```

**全部 100% 弃权** —— 但这**不是 bug，是正确行为**：实测该配置下
GSD ≈ **66.96 mm/px**（`camera_params` 兜底），系统只能可靠测量 **≥200.9 mm**
的东西；0.3mm 占 **0.00 px**、10mm 占 **0.15 px**，都远低于 3px 判读下限。
⇒ 系统**诚实地全部拒答**，符合 §2.3 的设计主张。

**教训**：只看「100% 弃权」会误判为缺陷；**必须把标定条件调好再看**，
否则测的是「标定不够」，不是「判据过严」。

---

## 三、第二次探针：把标定调到「10mm 可判」，问题才显形

`logs/_probe_rebar_lineclass2.py`，人造良好标定（`calib_object_px=4000`，
GSD ≈ **0.0525 mm/px**），抽样 60 张：

```
blob_10mm（10mm 判据）level 分布: {'measurement': 60}      ← 60/60 全部可判
crack_0.3mm（0.3mm 判据）level 分布: {'screening': 269}    ← 269/269 全部不到 measurement
```

| 类别 | 测量数 | 按**线状**判据弃权 | 按**块状**判据弃权 | 现行判据 |
|---|---|---|---|---|
| crack | 22 | **100.0%** | — | 线状 |
| spalling | 6 | — | 66.7% | 块状 |
| efflorescence | 31 | — | 54.8% | 块状 |
| **exposed_rebar** | 24 | **100.0%** | — | 线状 |
| **rust** | 150 | **100.0%** | — | 线状 |
| delamination | 19 | — | 36.8% | 块状 |
| moss | 17 | — | 29.4% | 块状 |

### ★ 结论

**即使标定好到「10mm 可判」，三类线状类仍然 100% 弃权**，而块状类的弃权率
只在 29–67% 之间。⇒ **假设成立**：

> **露筋（与锈迹）被归入线状类后，其分级结论是死代码 —— 永远输出 `unjudgeable`。**

---

## 四、根因（精确到数值）

- 0.3 mm 在 0.0525 mm/px 下只占 **5.7 px**，理论上够 3px 门槛，
  但**实际拍摄的成像质量**使 `crack_0.3mm` 停在 `screening` 级
  （`assess_interpretability(calib, 0.30)` 还含对比度/清晰度等因子）。
  ⇒ **0.3mm 判据本身就是「需要贴近拍摄 + 良好成像」的高门槛**。
- 露筋/锈迹的**物理语义**不是「发丝级宽度」：露筋是厘米级的暴露钢筋，
  锈迹是成片的锈蚀区。**用 0.3mm 去卡它们，量纲上就不匹配。**

## 五、修复方案（本轮已实现）

**把 `exposed_rebar` 与 `rust` 移出线状类，改按块状判据**（10mm），
但**保留 `crack` 在线状类**（裂缝的 0.3mm 判据是规范要求的、且语义正确）：

```python
LINE_CLASSES = ("crack",)                      # 只剩裂缝
BLOB_CLASSES = ("spalling", "efflorescence",
                "exposed_rebar", "rust",       # ← 从线状移入
                "delamination", "moss")
```

**为什么这样改是对的（三条独立理由）**：
1. **量纲匹配**：露筋/锈迹是面状或粗条带状缺陷，用 10mm 判读门槛与其物理尺寸匹配。
2. **可判读性可达**：改后它们在良好标定下能落到「可判 / 部分可判」，
   而不是恒 `unjudgeable`（死代码 → 活代码）。
3. **不放松安全**：10mm 仍是**分辨率可达的严门槛**，且
   **弃权的三条判据（图像质量 / 可判读性 / 窗口越界）一条不减**；
   改的只是「拿哪把尺子量」，不是「要不要拒答」。

⚠️ **同时必须更正的表述**：报告 §2.3 的类别表里
「`exposed_rebar` 露筋 线状 同裂缝」要改为「面状/粗条带状，按 10mm 判读门槛」。
（见 `logs/_PACK_WEIGHT_FIX_20260925.md` 同类纪律：改了行为必须同步改文档。）

## 六、★ 连带发现：`app.py` 里还藏着**第二份**弃权实现（§11.9 只修了一半）

改完 `grade.LINE_CLASSES` 后自检发现：**`06_deploy/app.py` 根本没用共享实现**。

```
$ grep -n "classify_unjudgeable|apply_abstention" 06_deploy/app.py
（无命中）
$ grep -n "from grade import" 06_deploy/app.py
171:    from grade import building_risk_level, grade_all      ← 只导入了这两个
```

`app.py` 在 `analyze()` 里**自己内联了一份 ~90 行的弃权逻辑**，其中：

```python
def _is_line(cls: str) -> bool:
    return cls in ("crack", "exposed_rebar", "rust")     # ← 旧的三元组，独立副本
```

### 这意味着什么（严重性）

报告 §11.9 标题是「弃权机制的一次真实缺陷修复：**从『只在界面里』到『全链路共享』**」，
但实际只完成了 **两处中的一处**：

| 入口 | 是否用共享实现 |
|---|---|
| `pipeline.py`（CLI / batch_screen / video_screen 都经它） | ✅ 已改为调用 `grade.classify_unjudgeable` |
| **`06_deploy/app.py`（界面）** | ❌ **仍是自己那份内联副本** |

⇒ 本次把 `grade.LINE_CLASSES` 收敛为 `("crack",)` 后，**若不同步改 app.py**，
就会出现：**CLI 说露筋可判、界面说露筋不可判** —— 正是 §11.9 想根除的那类缺陷。

### 修法

把 `app.py` 的那 90 行内联逻辑**删除**，改为委托共享实现
（`classify_unjudgeable` + `apply_abstention`），`app.py` 只保留：
- 渲染所需的 `_advise_for()`（补拍建议文本生成，作为 `advise_fn` 传入）；
- 着色、Markdown 等纯展示逻辑。

### 逐字段等价性验证（改界面**必须**做，否则视频过期）

因为改的是界面渲染路径，按纪律 #20 必须证明「输出文本没变」。
`logs/_verify_app_delegation.py` 用**旧内联实现的逐字复刻**与新共享实现逐字段比对：

| 场景 | reason | confidence_note | severity | 等级 | 结论 |
|---|---|---|---|---|---|
| A 裂缝-可判读不足 | ✅ | ✅ | ✅ | ✅ | 等价 |
| B 裂缝-窗口越界 | ✅ | ✅ | ✅ | ✅ | 等价 |
| C 图像质量不合格 | ✅ | ✅ | ✅ | ✅ | 等价 |
| D 块状类-可判读不足 | ✅ | ✅ | ✅ | ✅ | 等价 |
| **E 露筋（0.3mm 不足、10mm 够）** | **变** | **变** | **变** | **变** | **如预期（修复生效）** |

⇒ **A~D 逐字等价 ⇒ 界面渲染文本不变 ⇒ 已录的实机运行视频仍然有效。**
E 的「变」正是本次修复的目的（露筋不再被错误弃权）。

### ★ 顺带修掉的一处「重构引入的文本回归」

比对时发现共享实现与旧内联版有一处**文本差异**：

- 旧 `app.py`：`confidence_note` 的「【本次具体原因】…」是**条件追加**
  （只在 `窗口越界 or 质量不合格` 时加；纯「判读门槛不够」情形**不加**，
  因为正文前半句已说过同样的话）；
- 共享实现：原先**无条件追加** ⇒ 比旧界面更啰嗦。

⇒ 已在 `grade.apply_abstention` 里加 `_specific` 布尔量恢复原语义。
**这一处若不做等价性验证就发现不了**（它只在「纯判读门槛不够」这一分支出现）。

### 真跑验证

`logs/_smoke_app_analyze.py` 直接 import `app.analyze()` 喂 3 张真实测试图：
**全部 OK**，且每张的 markdown 都含「无法判定 / 等级 / 补拍建议」三者
（证明 `advise_fn` 契约正确、没有被 `except` 静默吞掉）。

## 七、诚实边界

1. **未改任何已上报的测试集指标**：本次改的是**弃权/分级判据**，
   不涉及模型权重、训练、mAP。测试集指标一个数字未动。
2. **改动会影响下游分级输出**：改后露筋/锈迹的 `severity` 不再恒为
   `unjudgeable`，可能出现 `danger/attention/normal`。
   ⇒ 这是**修复的目的**（把死代码变成活代码），不是副作用。
3. **界面渲染文本已验证不变**（A~D 逐字等价）⇒ **无需重录实机运行视频**。
   （仅当「露筋/锈迹实际被检出且可判读」这一新情形出现时，界面才会多出
   露筋的分级结论 —— 这是**功能增强**而非文本改动。）
4. **本次未做 100 轮的再验证**：因为这不是训练侧改动，无需重训。
5. **本实验的「人造标定」是受控条件**，不代表真实采集分布；
   它只用来**证伪「线状判据对露筋可达」**这一个命题。
6. **`measure.py::line_like` 有意保持三类不变** —— 它管的是**测量算法**
   （是否用黑帽 + 骨架化），与**判读门槛**是两个独立问题；已在 `grade.py`
   里写明注释防止后人「为了对齐」而误改。
