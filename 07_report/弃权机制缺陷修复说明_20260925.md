# 一个真实缺陷的发现与修复：弃权机制只在界面里生效

> 2026-09-25 · 外墙缺陷筛查工程
> 相关文档：技术报告 §2.3（原始设计）、§11.9（缺陷全过程）、§5.8（备忘录）

## 一句话

报告里写着「拒答必须传染到输出层」，但这段逻辑**只实现在 Web 界面里**，
命令行 / 视频 / 批量三个入口全部绕过它 —— 于是同一个系统会对同一张图
给出**自相矛盾的两套结论**。已定位、已修复、已验证。

## 缺陷长什么样（实测复现）

用 4 张测试图跑批量筛查，得到：

```
可判读性模块：crack 0.3mm → insufficient（不可判读）
分级模块：    裂缝宽 401.79mm > 限值 0.20mm → danger
汇总输出：    C（局部危房）
```

一条裂缝 401.79mm 宽，物理上不可能 —— 这就是矛盾的铁证。

**根因**：这些图并非按默认拍摄前提（20 m / 24 mm）拍摄，相机标定在信息不足时
仍给出了兜底值 GSD ≈ 66.96 mm/px。在这个尺度下，任何毫米数都被放大到荒唐量级。

## 为什么代码会这样

| 入口 | 实现 | 弃权是否生效 |
|---|---|---|
| `06_deploy/app.py` 的 `analyze()` | 自带完整弃权逻辑 | ✅ |
| `02_code/pipeline.py` 的 `run_one()` | `grade_all()` → `building_risk_level()` | ❌ **无闸门** |
| CLI（`pipeline.py --image`） | 走 `run_one` | ❌ |
| 视频筛查（`video_screen.py`） | 走 `run_one` | ❌ |
| 批量筛查（`batch_screen.py`） | 走 `run_one` | ❌ |

⇒ 报告 §2.3 说「这些条目不计入房屋危险性等级的升级判定」，
**对上面四个 API 入口都不成立**。这是「文档所述与代码行为不一致」，
比单纯算错更隐蔽：评审会以为弃权是全链路生效的。

## 修法：抽成单一共享实现

在 `02_code/grade.py` 新增两个函数，作为弃权的唯一实现：

- `classify_unjudgeable(measurements, interp_crack, interp_blob, quality)`
  → 逐条给出「是否弃权」的布尔标记（与输入等长同序）
- `apply_abstention(grades, measurements, flags, calib, quality, advise_fn)`
  → 作废定量结论 + **重写 `reason`** + 重新汇总等级

三条判据（与 `app.py` 逐字同义）：

1. 图像质量不达标（几何合格 ≠ 图像可用）
2. **该类**可判读性不达 `measurement` 级 —— 按线状/块状**分别**判，不搞一刀切
3. 测量窗口越界（低于 3px 或超出 ROI 可靠上界 `ks−1`）

`pipeline.run_one()` 改为调用这两个函数。
**`app.py` 本次未改动** —— 它的行为已与共享实现一致，且属于演示界面，
任何可见改动都需重录实机视频。两条路径的一致性由实测脚本保证（见下）。

## 验证（三组独立证据）

### 证据 1：修复前后对照（同一批 4 张图）

| | 修复前 | 修复后 |
|---|---|---|
| 建筑级风险 | **C（局部危房，6 条 danger）** | **U（无法判定，0 条 danger）** |
| 作废条目 | 未标识 | **29 条全部标记 `unjudgeable`** |
| 与可判读性结论 | **矛盾** | **一致** |

### 证据 2：跨入口一致性实测

`logs/_check_entrypoint_consistency.py` —— 把 API 路径与 UI 路径摆在一起跑：

```
[PASS] greybrick-yolo__1174.jpg obj_px=无:   API=U(弃权6) vs UI=U(弃权6)
[PASS] greybrick-yolo__1180.jpg obj_px=无:   API=U(弃权3) vs UI=U(弃权3)
[PASS] greybrick-yolo__1174.jpg obj_px=420:  API=U(弃权6) vs UI=U(弃权6)
ALL PASS
```

三条用例风险等级与弃权条数**逐一相同**。

### 证据 3：回归测试（含反向约束）

| 脚本 | 用例 | 关键反向用例 |
|---|---:|---|
| `logs/_test_abstention.py` | 9 | 「blob 可观 ⇒ **不**弃权」（防过度拒答） |
| `logs/_test_batch_screen.py` | 7 | 「苔藓（非结构类）**不**把建筑升到 C」 |

> ★ **反向用例当场抓到修复本身引入的第二个 bug**：第一版判据用了
> `n_defects == 0`，但该字段**含作废条**，导致全弃权时没报 `U`。
> 改为「有效条 = 总条数 − 弃权条 ≤ 0」后才通过。
> —— 只写正向用例的话，这个 bug 会漏网。

## 没改什么（边界声明）

- **未改动任何已上报的毫米测量值、模型权重、测试集指标。**
  修的是「输出层一致性」，不是重新评估指标。
- **未改动 `app.py`** ⇒ 已提交的实机运行视频仍然有效。
- 上文「C → U」是 4 张测试图的端到端演示，**不是**对 V3 测试集的重新评估。

## 沉淀

- 技能：`.workbuddy/skills/cross-entrypoint-claim-consistency/SKILL.md`
  —— 沉淀「机制只写在一个入口、文档却说是系统级」这一类 bug 的识别与修法。
- 三条通用纪律：
  1. **找一个物理上荒谬的数值**是暴露这类 bug 最快的办法（401.79mm 宽的裂缝）；
  2. 修机制不一致时**必须连 `reason` 文本一起重写**（只改 severity，荒唐数字仍会从文本漏出）；
  3. 回归测试**必须有「反向约束」用例**，防止修一个 bug 引入一个更宽的 bug。
