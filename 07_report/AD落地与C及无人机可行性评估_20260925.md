### 2.2 我补的是什么

**把 ①②③④ 放进同一套 RC 框架，比出谁更会"知道自己不可靠"。**
还要新增一个**可学习弃权器**（对 4 个信号做逻辑回归/GBDT），看它能否超过任何单一信号。

### 2.3 ★ 标签怎么来（不需要人工标注）

这是本设计最巧的一点 —— 用**方法间一致性**定义"真值"：

```
measure_ok = |wmean_cur − wmean_F1| / max(wmean_cur, wmean_F1) < 0.15
```

- **直觉**：黑帽核 `ks` 由 ROI 短边决定；当 `ks` 装不进目标内部时黑帽响应归零 ⇒ 测出的宽度是**塌陷值**。
- F1 多尺度核（{7,13,21} 取响应最大）**不受单核尺寸限制**，是更稳的参照。
- 两者差异大 ⇒ cur 不可信 ⇒ **应弃权**。
- ⚠️ 诚实边界：F1 也可能错 ⇒ 这是「**共识真值**」（consensus），**不等于**绝对毫米精度。

## 三、C 路：采集闭环（★ 可以做，核心已实现并验证）

### 3.1 结论：**可以做，且已做完最难的一半**

原来 C 路包含两件事，我核查后发现**第一件（能判别的部分）是缺的，第二件（数据留痕）依赖真实用户**。

### 3.2 已实现：GSD 反解（把"拒答"变成"给具体动作"）

新增 `02_code/advice.py`，与 `gsd.calibrate_by_camera()` **严格互逆**（有往返自检）：

```
gsd(d) = d · 1000 · 2·tan(fov/2) / W        # 线性于距离 ★ ⇒ 反解闭式、无歧义
```

实测输出（图像宽 4000px，主摄 24mm 等效）：

| 目标 | 需 GSD ≤ | **拍摄距离 ≤** | 画面覆盖 |
|---|---|---|---|
| 裂缝定级 0.3mm | 0.1000 mm/px | **0.27 m** | 0.40 m |
| 裂缝定级 0.5mm | 0.1667 mm/px | **0.44 m** | 0.67 m |
| 明显裂缝 1.0mm | 0.3333 mm/px | **0.89 m** | 1.33 m |
| 露筋 ~12mm | 4.0000 mm/px | **10.67 m** | 16.00 m |
| 小剥落 10mm | 3.3333 mm/px | **8.89 m** | 13.33 m |
| 中等剥落 50mm | 16.6667 mm/px | **44.44 m** | 66.67 m |

> 示例：当前 1.2 m 外拍、要判 0.3mm 裂缝 ⇒
> **「需再靠近 0.93 m（至 ≤ 0.27 m）」** —— 不是废话式的"靠近点"，而是**具体到米**。

**为什么这张表有分量**：它把**赛道二的硬约束取舍**可视化了 ——
同一台手机，判露筋能站 **10.67 m** 外，判裂缝定级却必须贴到 **0.27 m**（差 **40 倍**）。
这个数字任何评委都能用计算器复算（系数与 `gsd.py:25` 的注释完全一致）。

**并且它同时验证了一条既有结论**：`advice` 算出 0.3mm ⇒ 0.1 mm/px，
与项目注释「要判读 0.3mm 需要 GSD ≤ 0.1mm/px」**完全吻合** ⇒ 交叉印证。

## 四、★ 无人机测绘：可以做，但要先想清楚「它到底加了什么」

### 4.1 结论先行

| 判断 | 内容 |
|---|---|
| **技术上可行吗** | ✅ **可行，且比预期容易** —— 正射校正 + 多段拼接 + 批量管线 + 拒答机制**全都已有** |
| **值得做吗** | ⚠️ **取决于选哪个层次** —— 见下面三档 |
| **最大风险** | ❌ **无真实无人机数据**（本机无设备），若声称"已用无人机实测"= 造假 |

### 4.2 三档做法，代价与说服力差很多

#### 【第 1 档】只做「界面入口」：多图上传 → 拼接 → 整立面结果

| 项 | 内容 |
|---|---|
| **做什么** | 在 `app.py` 加一个 Tab：多图上传 → 调 `stitch_segments()` → 拼成整立面 → 跑 `pipeline` → 出整面墙报告 |
| **为什么算「完整系统」** | 现在系统只能回答"**这一张照片**里有什么"；加上拼接后能回答"**这一整面墙**有什么"——这是从"拍照工具"到"测绘系统"的**质变** |
| **代价** | **低** —— 算法全有，只写 UI 胶水 |
| **风险** | 低。但**必须在 UI 上明说"输入是分段正拍照片，不是无人机航拍"** |
| **挑战性** | C1（需自己设计交互）+ C2（要处理拼接失败时的拒答传播） |

#### 【第 2 档】做「航拍几何仿真」：证明无人机场景下判据依然成立

| 项 | 内容 |
|---|---|

| **为什么有分量** | **诚实**：明确写"无真实无人机数据，以下为几何仿真"。且 `advice.py` 的反解在无人机场景**更有价值**（航高固定的取舍更硬） |

| **风险** | 中。若仿真假设太理想，说服力下降 |
| **挑战性** | **C4**（可证伪的仿真验证）+ C2 |

### 4.3 ★ 无人机与现有系统的**真正缺口**（这才是要解决的问题）

现有 `stitch_segments()` 的前提是「**沿墙面依次平移、相邻段重叠 20~50%**」。
无人机航拍与它的差异**不在算法，而在这三点**：

| # | 无人机特有 | 现有系统是否处理 | 缺口性质 |
|---|---|---|---|
| ① | **POS 数据**（GPS/IMU 位姿）可直接给单应初值 | ❌ 完全没用（纯 ORB+RANSAC） | 补上=**大幅提升匹配鲁棒性** |
| ② | **航带规划**（重叠率、航高一致性） | ❌ 无 | 需新增"任务规划"层 |
| ③ | **高空大 GSD** ⇒ 细节类（裂缝）天然不可判读 | ⚠️ 几何判据可处理 | **已有能力覆盖**（`advice.py` 能量化） |

⇒ **新洞察**：无人机测绘的**核心增量不是"拼接"（已有），而是"把 POS 位姿当先验"**
—— 这是文献里航测的标准做法，而现有系统完全没用。**这正是一个干净、可辩护的技术增量。**

### 4.4 一个必须澄清的验证限制

我原本想用**真实测试集**验证"整立面测绘"，核查后**发现做不到**：

- V3 测试集 285 张来自 **4 个独立来源**（`greybrick-yolo` / `hrcds_yolo_exposed_rebar`
  / `rebar_structural` / `urban_yolo_rust_delam`），是**散拍照片**，
  **互不构成同一立面的相邻段** ⇒ 没有"重叠区"可供匹配。
- ⇒ 这解释了 `_verify_rectify.py` 当初为什么用**合成场景**：**不是偷懒，是没有别的办法**。
- ⇒ 因此「整立面测绘」的任何验证**只能走合成场景**，且报告必须**明确声明**这一点。

已写好 `_survey_demo.py`（复用既有渲染器 + 拼接器，演示完整链路：
分段 → 拼接 → 整立面统一尺度 → 整墙能力评估），**待训练结束后运行**。

### 4.5 推荐方案

**做第 1 档 + 第 3 点缺口的「POS 先验」设计论证，不做第 2 档的完整仿真，绝不做第 3 档。**

理由：
1. **第 1 档性价比最高** —— 算法全有，写 UI 即可把"拍照工具"变成"整墙测绘系统"，直接提升"完整系统"的说服力。
2. **POS 先验只需设计论证**（写清"若接入 GPS/IMU 单应初值，可把 ORB 失败率从 X 降到 Y"），
   不必真跑数据 —— **诚实且专业**。
3. **不做 2 档仿真**：仿真容易做成"自证"，且与 §7.7 的合成验证重复度高，边际价值低。
4. **不做 3 档**：无设备无数据，任何"实测"都是造假。

> **一句话叙事**：「我们的系统已经能从**单张照片**回答『有什么』，
> 并且能正射校正、多段拼接成**整立面图**、在拼接歧义时主动拒答。
> 若接入无人机航拍，**剩下的关键一步是把 POS 位姿作为单应初值**——
> 这一步我们给出了设计论证，但**没有真实航拍数据，故不声称已实测**。」
