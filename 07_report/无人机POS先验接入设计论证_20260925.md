# 无人机测绘接入设计论证（POS 先验作为单应初值）

> 撰写日期：2026-09-25
> 定位：回答「我们是不是可以做一个比较完整的系统，比如加上无人机测绘」。
> 结论先行：**可以，而且底座已经有约 80%。** 但真正缺的不是「拼接算法」，而是
> **「把无人机 POS 先验喂进单应求解」这一环** —— 现有 `stitch_segments()` 是**盲匹配**，
> 没有位姿先验入口。本文给出该环的设计、与现有代码的接缝、以及**诚实的边界**。
>
> **★ 状态更新（同日晚）：第二、三、四节的设计已落地实现并合成验证 → 见第六节。
> 第 1 层（后端 POS 先验）状态从「已设计」升级为「已实现（合成验证）」；
> UI 入口与真机数据仍为未完成项。**

### 1.2 真正的缺口：`stitch_segments` 没有位姿先验入口

看签名：

```python
def stitch_segments(images: list, max_features=4000,
                    min_inliers=12, min_inlier_ratio=0.15)
```

它**只接受一串图像**，内部靠 ORB 特征 + RANSAC 盲求相邻段之间的单应。这在
**手机手持**场景是对的（本来就没有位姿信息可给）。但无人机**有 POS**：

| 无人机能给的量 | 典型来源 | 对求解的用处 |
|---|---|---|
| 经纬度 / 相对位置 | RTK-GNSS 或视觉里程计 | **约束平移分量** |
| 航向角 yaw | IMU / 云台 | **约束旋转分量** |
| 俯仰 / 横滚 pitch/roll | IMU / 云台 | **约束仿射/透视分量** |
| 离墙距离 d | 激光测距或 GNSS+墙面先验 | **直接给出尺度（GSD）** |

⇒ 现状是**把这些信息全扔了**，退回盲匹配。这是「无人机测绘」与「手机拼接」的**唯一实质差别**，
也正是可写进报告的**技术增量点**。

## 二、设计：POS 先验作为单应初值（而不是替代品）

### 2.1 核心思路 —— 「先验给初值，特征做精修」

```
无人机 POS (lat,lon,alt,yaw,pitch,roll,d)
        │
        ▼  ① 投影模型：把墙面当作已知平面（世界坐标已知）
   初始单应 H0 = π(K, R, t, plane)          ← 解析可算，无需特征
        │
        ▼  ② 用 H0 把第 j 段 warp 到第 i 段坐标系
   初始化重叠区
        │
        ▼  ③ 只在重叠区内做特征匹配 + RANSAC
   增量修正 ΔH，得到 H = ΔH · H0
        │
        ▼  ④ 用现有周期混叠检测（_alias_gap）兜底
   若修正量与 H0 偏差过大 ⇒ 判「不可靠」，拒答
```

**为什么是「初值」而不是「直接用它」**：POS 有漂移（民用 GNSS 米级、IMU 累积误差），
不足以单独定标；但它足够好到**把特征匹配限制在正确的重叠区**，从而
(a) 大幅降低误匹配，(b) 让纯周期砖面（S1/S4/S6 会失败的那些）**有可能**拼对
—— 因为此时不再依赖「图案唯一性」来消歧，而依赖「位姿把两段放到大致正确的位置」。

### 2.2 与现有代码的接缝（改动最小化）

**新增一个可选参数，不破坏现有调用**：

```python
def stitch_segments(images: list,          # 保持原签名不动
                    max_features=4000, min_inliers=12, min_inlier_ratio=0.15,
                    poses: list | None = None,     # ← 新增：每段的 (yaw, pitch, roll, d)
                    K: np.ndarray | None = None):  # ← 新增：相机内参（可标定）
    ...
    if poses is None:
        # 原路径：盲匹配（手机手持），行为完全不变
        ...
    else:
        H0 = _homography_from_pose(poses[i], poses[j], K)   # 解析初值
        # 在 H0 邻域内做匹配（可给 RANSAC 一个 "接近 H0" 的先验权重）
        ...
```

**关键纪律**：`poses=None` 时**逐字节保持现状行为** —— 这样
- 现有 S1–S6 验证**全部照常通过**（它们是手机场景，不给 poses）；
- app.py 的现有「正射校正」单选**行为不变**；
- 新增能力是**纯增量**，可以单独开关、单独验证。

### 2.3 验证方案（必须，且**不能用 V3 测试集**）

⚠️ **V3 测试集无法验证拼接**：285 图来自 4 个独立来源，是**散拍照片**，
不是同一立面的相邻分段 ⇒ 任何「拼得好不好」的验证**在真实测试集上做不了**。
（这正是 `_verify_rectify.py` 用合成场景的原因，不是偷懒。）

⇒ 验证分两层：

| 层 | 数据 | 验什么 |
|---|---|---|
| **合成层（必做）** | 扩展现有 S1–S6：给合成分段**注入已知 POS**（无噪声 / 加噪声 / 加漂移三档） | 拼接精度 vs POS 误差的**关系曲线** |
| **真实层（如能拿到）** | 若日后有真机航拍序列，做定性核对 | 不写定量结论，只报「可跑通」 |

**合成层的可证伪点**（这才是有价值的部分）：注入**故意错误**的 POS，
应观察到「修正量 ΔH 偏大 → 触发拒答」⇒ 证明**POS 不可信时系统会兜底**，
而不是「照着错 POS 拼出错的立面还宣称成功」。

## 三、三层「完整系统」的取舍（我的建议：只做第 1 层 + 设计论证）

| 层级 | 内容 | 成本 | 我的判定 |
|---|---|---|---|
| **第 1 层** | 多图上传 UI 入口（把已有的 `stitch_segments` 接到界面）+ 本文设计论证 | 低（~1 天） | **✅ 做** |
| **第 2 层** | 完整无人机测绘仿真（POS 注入 + 精度曲线 + 报告章节） | 中（~3–5 天，且需重录视频） | **⏸ 缓做**，除非时间宽裕 |
| **第 3 层** | 声称「我们做了无人机测绘」 | —— | **⛔ 不做**。我们**没有真机数据**，声称即造假 |

### 为什么第 1 + 设计论证是**性价比最高**的

1. **底座已有 80%**，第 1 层只是「把现有能力接到界面」，风险极低。
2. **设计论证是「未来工作」章节最硬的内容** —— 它证明我们**知道**缺口在哪、
   **知道**怎么补、**知道**怎么验证，且**明确区分**「已实现」与「已设计未实现」。
   评委会认可这种区分，反而比含糊声称「我们做了完整系统」更可信。
3. ⛔ **第 3 层的诱惑必须抵抗**：答辩现场一旦被问「真机数据呢」，声称即崩。

### 与 §5.6 先例核查的一致性

无人机立面测绘**不是新领域**（已有大量 photogrammetry 工作），我们的增量**不在**「做了无人机」，
而在**「把 POS 先验作为单应初值，并在 POS 不可信时用现有周期混叠检测兜底拒答」** ——
这是把 §5.6 那四条系统层增量（几何弃权 / 按类判定 / 拒答传染 / 输出 U）**延伸到测绘环节**。
**答辩口径**应当是后者，不是前者。

## 四、诚实边界（必须写进报告，不能说满）

1. **无真机数据**：所有测绘结论若给出，都基于**合成场景**；真实航拍序列未获取。
2. **POS 精度未标定**：`_homography_from_pose` 的容错范围依赖 POS 误差量级，
   而这个量级**本项目没有实测**（需真机 RTK 数据才能标定）。
3. **单平面假设**：把墙面当平面。真实立面有凹凸（阳台、空调机位）⇒ 大透视下会引入形变。
4. **拼接的绝对尺度**仍依赖 GSD 标定（测距或砖缝周期），POS 的 alt 不能直接当尺度用
   （除非有墙面到飞行器的精确距离）。
5. **不宣称「已实现无人机测绘」** —— 只写「已实现多段立面拼接；已设计无人机 POS 接入方案，
   未获取真机数据验证」。

### 6.2 ★ 一个重要的设计修正（从「过滤」改为「仲裁」）

初版设计（2.1 节流程图）设想「用 H0 把特征匹配限制在重叠区」。**实测证否**：
以 H0 为中心、3% 对角线为半径过滤 ORB 匹配，1694 对里只剩 **1–4 对** ——
因为 ORB 匹配本身就没在盲匹配阶段对齐，H0 也救不回来。**该做法已废弃。**

**改用「POS 仲裁周期性混叠」**（这才是先验的正确用法）：

- 当周期面触发混叠时，系统本来就有两个候选单应（`Hc` 选中解 / `Hr` 对手解）；
- 用 H0 分别量两者的四角偏离；
- **Case A**：H0 支持选中解 ⇒ 据此**解除混叠**（`confirm_selected`）；
- **Case B**：H0 明显支持对手解 ⇒ **切换到对手解**（`switch_to_rival`）；
- 两者差距 < `POS_ARB_MIN_GAP_PX`(20 px) ⇒ 不介入，保持原拒答。

**实测效果（S7）**：POS 介入前失败原因是「周期性混叠」，
介入后**混叠被解除**，失败原因变成「内点 219/1694（12.9%）低于 15% 门槛」——
即**先验确实打破了歧义**，残留阻塞是原始的内点率门槛（与 POS 无关）。
这是一个**诚实的部分成功**：证明 POS 能消歧，但不足以单独让纯周期面通过。
