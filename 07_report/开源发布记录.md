## 二、怎么自己验证（不需要相信本文档）

### 2.1 方法一：浏览器直接看（最简单）

打开 <https://github.com/dutanlu/wall-defect-screening>
→ 应能看到 `02_code/`、`04_results/`、`05_quantify_grade/`、`06_deploy/`、
`07_report/`、`README.md`、`LICENSE`、`LICENSE-NOTES.md`、`requirements.txt` 等。

### 2.2 方法二：命令行核对提交是否一致

```bash
git ls-remote https://github.com/dutanlu/wall-defect-screening.git HEAD
# 输出一个 40 位提交号，例如：3aa5db9e887a6195a2c65e04c492d8a24c14b65b    HEAD

# 与 API 返回的 sha 交叉印证（两者必须一致）：
curl -s https://api.github.com/repos/dutanlu/wall-defect-screening/commits/main
```

### 2.3 方法三：用 GitHub API 统计「文件数与体积」并检查有无泄漏（本文档采用的证据）

```bash
curl -s "https://api.github.com/repos/dutanlu/wall-defect-screening/git/trees/main?recursive=1"
```

把返回 JSON 里的 `tree` 数组筛出 `type == "blob"` 的条目，
统计条数（= 文件数）与 `size` 之和（= 体积）。实测结果见 §三、§四。

> **为什么用这个方法而不是肉眼数**：肉眼只能看到目录列表，
> 既数不准文件数，也**发现不了「某个大文件混进来了」**。
> trees API 能拿到每个文件的**字节数**，可以直接做筛选断言。

### 5.1 网络

发布前实测：`github.com` 直连超时、系统代理返回 `502`
（校园网出口封锁）。**发布当日网络已恢复**（`github.com` 返回 200，
`git ls-remote` 成功），故得以完成发布。

### 5.2 凭据（为什么最终是用 GitHub Desktop 发布的）

排查发现三条命令行凭据路径**全部不可用**：

| 方案 | 结果 |
|---|---|
| 默认（无 helper） | `could not read Username for 'https://github.com': terminal prompts disabled` |
| GitHub Desktop 自带 `git-credential-desktop` | `ERROR: Missing DESKTOP_PORT environment variable` —— 它依赖 Desktop 的进程间通信，**不能独立调用** |
| Windows 凭据管理器 `wincred` | **超时**（想弹窗要凭据，但无交互终端） |

⇒ **根因**：GitHub Desktop 的 OAuth 凭据保存在它自己的加密存储里，
既不写入 Windows 凭据管理器，也不提供可独立调用的 helper。
「Desktop 发布」与「命令行推送」是**两条互不相通的凭据路径**。
